## 把工程管理判断变成可复用的 AI 工作流

我把这些年写下的技术规划、指标度量、方案评审和管理沟通方法，整理成了一组可以由 AI Agent 按任务调用的 Skills。它们不负责替人做组织决策，而是把容易在忙碌中丢掉的判断步骤保留下来：要改变什么结果，当前证据是什么，约束和取舍在哪里，谁需要作决定，以及什么信号会让我们重新判断。

目前这组 Skills 包含四个独立能力：

- **技术规划（`tech-planning`）**：从业务目标、用户问题和工程约束出发，比较投资选项，说明做什么、暂缓什么，以及何时根据新证据调整路线图。
- **指标决策（`metric-decision`）**：先定义指标实际测量的用户任务，再核验口径和数据质量；区分观察到的变化与尚未证实的原因，最后设计能验证下一步行动的办法。
- **技术评审（`tech-review`）**：评审已有方案中的证据、权衡和交付风险。每项重要意见都需要对应依据、影响和建议动作；没有阻塞项时，也可以给出通过结论。
- **工程汇报（`eng-reporting`）**：根据读者和用途组织项目事实，保留来源、估算和未知状态，让汇报能够支持判断、协作或行动，而不只是压缩原始材料。

它们可以单独使用，也可以在任务确实跨环节时组合：例如先用指标决策确认效果证据，再据此调整技术投资；或者评审方案后，把已确认的结论整理成管理层可用的同步材料。它不是必须按顺序执行的流程，也不是一个包办工程管理的万能助手。

这组方法的出发点来自我自己的写作。技术规划文章讨论如何从业务与竞争环境推导工程选择；指标文章从用户任务和测量对象开始；周期复盘强调保留口径、版本与上下文；管理沟通文章强调信息的目标是让特定读者能够作决定。整理成 Skills 的过程，则进一步要求把这些判断写成短而可调用的入口、可单独安装的目录和能暴露失效方式的测试用例。

目前仓库为四项 Skills 准备了 24 个场景用例，覆盖缺数据、信息冲突、正常任务和决策压力。对其中六个代表性场景做过无技能与启用技能的单轮对照：基础模型本身已经能正确处理一些问题，技能的可见价值更多是让证据状态、评审字段和行动条件更一致。这些测试是定性烟雾检查，尚不能证明跨模型、跨任务的效果提升。

我想探索的不是让 AI 写得更像一个强势的技术负责人，而是把自己的判断方法从文章里提炼出来，让它在具体工作里更容易被调用、检查和修订。
